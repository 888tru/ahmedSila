# Суперадминка — технологический стек и архитектура

> Внутренняя панель управления клиентами (тенантами) — магазинами и супермаркетами,
> использующими наш продукт для автоматизации задач и смен сотрудников (MVP).
> Суперадминка — это инструмент нашей команды: видим тенантов и верхнеуровневые
> показатели (сотрудников в системе, последнюю активность), обрабатываем обращения
> в поддержку, управляем доступом собственной команды.
>
> Суперадминка **не видит продажи и выручку тенанта** — этих данных у продукта нет
> и не будет по архитектуре. Закупки — другое дело: в будущем целевой сервис
> добавит модуль заявок (оператор оформляет заявку на закупку товара у поставщика —
> что, сколько, по какой цене — админу магазина), и эти данные будут агрегироваться
> в суперадминку как показатель закупочной активности клиента. Схема БД и gRPC-
> контракт под это закладываются уже сейчас, при проектировании MVP (см. §6, §6a) —
> реализация в целевом сервисе всё равно откладывается на следующую фазу, но
> суперадминка не должна потом переделывать модель данных под это. Это данные
> о закупках у поставщиков, не о продажах покупателям — разные вещи, см. также
> `DESIGN_BRIEF.md` и `PAGES.md`.
>
> Целевой сервис (тот софт, которым пользуются сами магазины — операторы, кассиры
> и т.п.) будет писаться отдельно, после суперадминки. Контракт между ними — gRPC;
> сам `.proto` проектируется, когда работа дойдёт до интеграции (см. §6a), а не
> заранее отдельным шагом.

## 1. Backend

**Нагрузочный профиль.** Суперадминка — внутренняя панель, её пользователи —
сотрудники нашей команды (десятки человек, не десятки тысяч). Высокая нагрузка
ожидается в **целевом сервисе**, а не здесь. Поэтому выборы ниже обоснованы
надёжностью, типобезопасностью и контролем над кодом — но не пропускной
способностью: аргумент «под высокую нагрузку» к самой суперадминке неприменим.

| Компонент | Технология | Причина выбора |
|---|---|---|
| Язык | **Go** | Индустриальный стандарт для инфраструктурных сервисов, компилируется в статический бинарник, дешёвый деплой в контейнерах |
| Веб-фреймворк | **Gin** | Зрелый Go-фреймворк, много готовых middleware, низкий порог входа для новых разработчиков в команде |
| База данных | **PostgreSQL** | Надёжность, зрелость, предсказуемое поведение. Репликация и read replicas — не в MVP, добавляются, когда появится метрика, которая их требует |
| Доступ к БД | **sqlc** | Пишем чистый SQL → генерируется типобезопасный Go-код. Полный контроль над запросами, никакой ORM-магии |
| Кэш / очереди | **Redis + asynq** | Rate limiting, revocation list для JWT, фоновые задачи (asynq — аналог Sidekiq для Go): снятие метрик тенантов, reconciliation провижининга (см. §6a) |
| Аутентификация | **JWT (access + refresh)** | Access token — короткий TTL (15 мин) с зашитыми правами (claims). Refresh token — ротируется при каждом использовании, с детектом переиспользования |
| Авторизация | **Casbin (RBAC)** | Роли внутри команды суперадминки: `owner / admin / support / viewer` |
| 2FA | **TOTP** | Обязательно для аккаунтов с полным доступом (owner/admin) |
| Межсервисное взаимодействие | **gRPC + Protobuf** | Строгая типизация контрактов с целевым сервисом, бинарный протокол быстрее JSON, поддержка стриминга для live-метрик |
| Proto-тулинг | **buf** | Линтинг `.proto`, детект breaking changes, генерация кода |
| Внешний API | **REST (Gin)** | Наружу — для фронтенда суперадминки |
| Логирование | **zerolog** | Structured logging, быстрее стандартного `log` |
| Метрики | **Prometheus + Grafana** | Мониторинг latency, error rate, состояния фоновых задач |
| Трейсинг | **OpenTelemetry** | Сквозная трассировка запросов через слои и gRPC-вызовы |
| Отказоустойчивость | **sony/gobreaker** | Circuit breaker на gRPC-клиентах к целевому сервису — деградация, а не каскадное падение |

### Два независимых контура аутентификации

Их важно не путать — это разные пользователи, разные токены, разные точки входа:

1. **Контур команды** — сотрудники нашей команды входят в суперадминку.
   Роли `owner/admin/support/viewer`, проверка прав через Casbin, TOTP для
   owner/admin. Токены валидирует сама суперадминка.
2. **Контур тенантов** — сотрудники магазинов (операторы, кассиры) входят
   в целевой сервис. Суперадминка выступает для них issuer'ом токенов
   (по сути — IdP), целевой сервис их проверяет. Описано ниже.

### Контур тенантов: доступ к целевому сервису

Выбран **вариант C — JWT с правами + revocation list в Redis**:

1. Суперадмин заводит тенанта → тенант получает доступ через свою учётку
2. При логине выдаётся JWT (короткий TTL, 15 мин) с claims (тенант, роль, права)
   и уникальным `jti`. Подпись целевой сервис проверяет **криптографически, по
   публичному ключу** — без сетевого запроса в суперадминку. Ключи публикуются
   через JWKS-эндпоинт, ротация ключей — по расписанию с overlap-периодом
3. Проверка отзыва — lookup `jti` в Redis. Это **единственный сетевой поход**
   на пути запроса: суперадминка в критическом пути не участвует, но Redis —
   участвует. Формально это дешевле HTTP-интроспекции токена, но «без сети»
   схема не работает
4. Мгновенный отзыв доступа (например, при просрочке оплаты): `jti` попадает
   в Redis с TTL = остатку жизни токена (так blacklist не растёт), целевой сервис
   перестаёт пускать в течение долей секунды, не дожидаясь истечения TTL

**Решения, которые нужно зафиксировать до реализации** (см. §9):

- Redis для revocation list — общий с суперадминкой или отдельный инстанс
  у целевого сервиса с репликацией отзывов?
- Поведение при недоступности Redis — **fail-open** (пускаем, рискуя пропустить
  отозванный токен) или **fail-closed** (магазин встаёт целиком)? Умолчания тут
  нет, это продуктовое решение.

### Multi-tenancy

Суперадминка **сама не multi-tenant** — это единая внутренняя панель команды,
видящая всех клиентов. Изоляция данных (RLS) понадобится **в целевом сервисе**,
где данные одного магазина не должны быть видны другому. В суперадминке доступ
разграничивается через Casbin-роли внутри команды.

## 2. Архитектура backend — Clean Architecture

```
/cmd
  /server                    — точка входа, инициализация DI, конфигурации
/internal
  /domain                    — сущности и интерфейсы, без зависимостей от фреймворков
    tenant.go                — Tenant, TenantStatus, TenantPlan
    super_admin.go           — SuperAdminUser, Role
    support_ticket.go        — SupportTicket, TicketMessage
    audit_log.go             — AuditLog
    errors.go                — доменные ошибки (см. «Модель ошибок» ниже)
  /usecase                   — бизнес-логика, оперирует интерфейсами domain
    tenant_usecase.go        — CreateTenant, SuspendTenant, ListTenants...
    auth_usecase.go          — Login, RefreshToken, RevokeSession
    support_usecase.go       — CreateTicket, AssignTicket, ReplyToTicket
  /repository                — реализация интерфейсов domain поверх sqlc
    postgres/
      tenant_repo.go
      super_admin_repo.go
      support_repo.go
      audit_repo.go
    sqlc/                    — сгенерированный sqlc код (не редактировать руками)
  /delivery
    /http                    — Gin handlers, роутинг, middleware
      handler/
      middleware/             — JWT validation, RBAC-check, logging, recovery
      router.go
    /grpc                     — gRPC server/client для целевого сервиса
      server.go               — входящие вызовы от целевого сервиса
      client.go               — исходящие вызовы (провижининг, метрики)
                                реализуется вместе с контрактом, см. §6a
  /pkg                        — переиспользуемые внутренние утилиты
    jwt/                      — issuing/validation
    casbin/                   — конфигурация RBAC-модели и политик
    redis/                    — обёртка над клиентом, revocation list
    config/                   — viper-конфигурация
/migrations                   — SQL миграции (создаются вместе с domain-слоем, см. §6)
/proto                        — .proto контракты (появляются на этапе §6a)
/gen                          — сгенерированный protobuf/grpc код, генерится через buf
```

**Правило зависимостей**: `delivery → usecase → domain ← repository`.
`domain` не знает ни о Gin, ни о sqlc, ни о gRPC — это чистые Go-структуры и интерфейсы.
`usecase` знает только про интерфейсы `domain`, не про конкретную БД или HTTP.
`repository` и `delivery` — единственные слои, которые касаются внешнего мира
(PostgreSQL, Redis, HTTP, gRPC).

### Модель ошибок

Доменные ошибки объявляются в `domain/errors.go` (`ErrNotFound`, `ErrConflict`,
`ErrForbidden`, `ErrValidation`, ...). Слой `delivery` — единственный, кто знает
про HTTP-статусы и gRPC-коды: маппинг доменной ошибки в код и в единый JSON-формат
ответа живёт в одном месте, а не в каждом хендлере.

### Принцип: расширяемость через дизайн, а не через преждевременный функционал

Для MVP строим только то, что реально нужно сегодня — но так, чтобы будущие
enterprise-возможности (SSO, SCIM, гранулярные права под конкретного крупного
клиента, SOC 2-аудит) добавлялись без переписывания. Это не "заранее написанный
неиспользуемый код", а просто правильные границы:

- Аутентификация — через интерфейс (`AuthProvider`), MVP реализует только
  `PasswordAuthProvider`. SSO позже — это новая реализация того же интерфейса,
  `usecase`-слой не меняется.
- Авторизация — через интерфейс `Authorizer` поверх Casbin policy, не через
  `if user.Role == "admin"` в коде. Более гранулярные права под клиента — это
  изменение policy, не кода.
- `audit_logs` пишет каждое действие с самого начала (actor, action, metadata) —
  это и есть доказательная база для будущего SOC 2-аудита, без дополнительного
  функционала.
- Статусы/планы/типы — через Postgres enum, не строки — новый план или статус
  добавляется миграцией, не рефакторингом.

Всё, что не про архитектурные границы, а про конкретный функционал (сам SSO,
сам биллинг с dunning-логикой, status page) — НЕ строится в MVP, добавляется
когда появится реальный клиент, которому это нужно.

Этот же принцип применяется к инфраструктуре (§4): инструмент берётся под
существующую задачу, а не под ожидаемую.

## 3. Frontend

| Компонент | Технология | Причина выбора |
|---|---|---|
| Язык/фреймворк | **React + TypeScript (Vite)** | Стандарт для дата-интенсивных SPA |
| Мета-фреймворк админки | **Не используется** | Refine рассмотрен и отклонён (§9): для 6–8 CRUD-экранов его соглашения (dataProvider, authProvider, свой роутинг) стоят дороже, чем экономят, а TanStack Query у нас и так есть |
| Дизайн-система | **shadcn/ui + Tailwind CSS** | Компоненты копируются в проект и полностью кастомизируются — избегаем шаблонного "ИИ-генеричного" вида, в отличие от коробочных enterprise-китов вроде Ant Design |
| Работа с данными | **TanStack Query + TanStack Table** | Кэширование, инвалидация, синхронизация с REST API суперадминки; таблицы тенантов и аудита |
| Формы | **React Hook Form + Zod** | Типобезопасная валидация форм (создание тенанта, тикетов и т.п.) |
| Графики/метрики | **Tremor** или **Recharts** | Для будущего дашборда закупочной активности тенантов (после MVP, см. §6a) |

### Принципы дизайна (см. также `frontend-design` skill)

- Не использовать дефолтные ИИ-паттерны (кремовый фон + terracotta акцент,
  тёмный фон + один яркий акцент, broadsheet-вёрстка) без обоснования брифом
- Один продуманный "сигнатурный" элемент дашборда, остальное — сдержанно
- Структурные элементы (нумерация, метки) должны нести смысл, не декорацию

## 5. Порядок реализации (MVP)

1. **Схема БД + gRPC-контракт** — проектируются вместе (§6, §6a), включая
   `tenant_procurement_snapshots` под будущие закупки — сразу, не задним числом
2. **Core auth/RBAC** — модели SuperAdminUser/Role, Casbin policy, JWT issuing,
   Redis revocation list
3. **Управление тенантами** — CRUD, статусы, аудит-лог всех действий
4. **Поддержка** — тикеты и переписка с клиентами
5. **Frontend** — React + TanStack + shadcn/ui поверх REST API. Начинается
   после того, как бэкенд закрыт: до этого момента API проверяется curl'ом и тестами
6. **gRPC-реализация с целевым сервисом** — сервер/клиент по уже готовому
   контракту, когда целевой сервис реально появится (см. §6a)

## 6. Схема БД

Проектируется и генерируется вместе с domain-слоем (модель → миграция создаются
в одном шаге, не отдельно заранее). Ориентировочный набор сущностей:
`super_admin_users`, `refresh_tokens`, `tenants`, `tenant_procurement_snapshots`,
`support_tickets`, `support_ticket_messages`, `audit_logs`. Миграции — через
`goose` или `atlas` поверх `sqlc` (выбор — см. §9).

`tenant_procurement_snapshots` — агрегированные данные по заявкам на закупку
(что и по какой цене клиент заказывает у поставщиков через целевой сервис):
период, товарная позиция, количество, цена закупки. Таблица создаётся уже в
MVP-миграции, даже если целевой сервис (источник этих данных) появится позже —
чтобы схема не переделывалась задним числом. Пока целевого сервиса нет, таблица
просто пустая, дашборд показывает соответствующее пустое состояние (см. `PAGES.md`).

Денежные величины (цена закупки) хранятся в минорных единицах (`bigint`) или
`numeric`, никогда не в float. Валюта хранится явным полем.

## 6a. gRPC-контракт с целевым сервисом

Целевой сервис (софт для сотрудников магазинов — задачи/смены в MVP, заявки на
закупку в следующей фазе) будет писаться отдельно, позже. Контракт (`.proto`)
между суперадминкой и целевым сервисом проектируется уже сейчас, вместе со
схемой БД (§6) — это осознанное исключение из общего принципа «не проектировать
контракт заранее» (§2): закупки настолько важны для дашборда суперадминки, что
модель данных должна быть согласована с самого начала, чтобы не переделывать её
после того, как целевой сервис появится. Сама реализация gRPC-вызовов (сервер,
клиент, подключение) откладывается на этап, когда целевой сервис реально
существует — контракт фиксируется, код под него — нет.

Суперадминка должна уметь:

- провижинить/приостанавливать/удалять тенанта в целевом сервисе
- получать от целевого сервиса верхнеуровневые данные тенанта: количество
  сотрудников, последняя активность (MVP), и данные по заявкам на закупку
  (товар, количество, цена) для дашборда закупочной активности, включая
  live-обновления (стриминг)

Продаж/выручки клиента в этих данных нет и не будет — суперадминка не имеет
к ним доступа по архитектуре продукта.

### Согласованность состояния (провижининг)

«Создать тенанта» — это запись в нашу БД **плюс** gRPC-вызов в целевой сервис,
то есть распределённая операция: вызов может упасть после успешной записи.
Circuit breaker гасит каскад, но рассогласование не чинит.

Модель — **desired vs observed state**: у тенанта есть `desired_status`
(чего хочет суперадмин) и `observed_status` (что подтвердил целевой сервис).
HTTP-запрос меняет только `desired_status`; фоновая задача (asynq) сводит
состояния и повторяет вызовы до успеха. Все вызовы провижининга идемпотентны
по ключу тенанта. Это же решает «отозвать доступ при неоплате» — отзыв становится
таким же изменением desired-состояния, а не отдельным механизмом.

### Метрики в дашборде

Снапшоты метрик снимаются фоновой задачей по расписанию в
`tenant_metrics_snapshots` (частота — решить при реализации, ориентир: раз в час,
плюс on-demand refresh из UI). Если целевой сервис недоступен, дашборд показывает
последние известные значения с явной меткой времени и признаком устаревания —
не пустой экран.

## 7. Безопасность

### Secrets management

Секреты никогда не попадают в Git и не хранятся как plain env vars в манифестах.

- **Если остаёмся в одном облаке** (наиболее вероятно для MVP): нативный secrets
  manager этого облака — AWS Secrets Manager / GCP Secret Manager / Azure Key Vault.
- **Если хостимся сами / в k8s**: **Infisical** (core — MIT, каталог `ee/` под
  отдельной enterprise-лицензией; self-host или облако) + **External Secrets
  Operator** в Kubernetes.

HashiCorp Vault сознательно не берём — с 2023 он на Business Source License
(не open source) и требует значительно больше операционных затрат на поддержку
кластера.

Выбор варианта следует из решения по хостингу (§9).

### Сетевой периметр

- WAF перед публичным REST API (Cloudflare / AWS WAF)
- mTLS между внутренними сервисами (суперадминка ↔ целевой сервис по gRPC)
- gRPC-порты не выставляются наружу — только во внутренней сети
- DDoS-защита на уровне CDN/облака

### Приложение (OWASP Top 10)

- Валидация входных данных на обоих концах (Zod на фронте, аналогично на бэке)
- sqlc → параметризованные запросы по умолчанию (защита от SQL-инъекций)
- Строгий CORS whitelist, CSP-заголовки
- Rate limiting на login endpoint через Redis — защита от brute-force
- Lockout после N неудачных попыток входа
- Ротация refresh-токенов с детектом переиспользования: предъявление уже
  использованного refresh-токена = сигнал компрометации, вся сессия отзывается

### Supply chain

- Dependabot/Renovate — автообновление зависимостей с уязвимостями
- govulncheck в CI — сканирование Go-зависимостей на известные CVE
- Trivy — сканирование Docker-образов перед деплоем
- Pin-нутые версии зависимостей

### Hardening инфраструктуры

Применяется по факту выбранной платформы (§4): для managed-контейнеров —
минимальные IAM-права сервисного аккаунта и приватная сеть до БД; при переходе
на Kubernetes добавляются Network Policies (deny-all по умолчанию), Pod Security
Standards (контейнеры не от root) и k8s RBAC — отдельно от Casbin-RBAC приложения.

### Мониторинг и реакция на инциденты

- Prometheus/Grafana + OpenTelemetry (уже в стеке) + алерты на аномалии
  (всплеск 401/403, аномальная активность с одного IP)
- Sentry (или аналог) для error tracking в реальном времени
- Логи хранятся отдельно от продакшн-БД

### Данные и бэкапы

- Регулярные бэкапы PostgreSQL + периодическое тестирование восстановления
  (бэкап, который ни разу не восстанавливали — не бэкап)
- Шифрование данных at rest
- Forward + rollback стратегия для каждой миграции БД
- `audit_logs`: срок хранения и правила по PII в поле `metadata` фиксируются
  до первого продакшн-релиза (см. §9)

## 8. Тестирование

- `usecase` — unit-тесты поверх моков интерфейсов `domain` (внешних зависимостей
  нет по построению, это главная выгода от выбранных границ слоёв)
- `repository` — интеграционные тесты на реальном Postgres через testcontainers,
  прогон в CI
- `delivery/http` — тесты хендлеров, включая маппинг доменных ошибок в коды ответа
- gRPC — contract-тесты против `.proto`, появляются вместе с интеграцией (§6a)

## 9. Открытые решения

Пока эти вопросы не закрыты, зависящие от них разделы — гипотезы, а не план.

| Вопрос | Зависит от него | Когда решать |
|---|---|---|
| Хостинг: облако (AWS/GCP) или собственная инфраструктура | Secrets manager (§7), WAF, оркестрация (§4) | До начала деплоя, желательно до первого CI-пайплайна |
| Redis для revocation list: общий или отдельный у целевого сервиса | §1, контур тенантов | До реализации контура тенантов |
| Поведение при недоступности Redis **в контуре тенантов**: fail-open или fail-closed | §1 | Там же |
| Частота снятия метрик тенантов | §6a | При реализации дашборда |
| Срок хранения `audit_logs` и правила по PII | §7 | До первого продакшн-релиза |
| Платёжный провайдер: Stripe / Kaspi / Freedom Pay | §10 | Когда появится первый платящий клиент |

### Закрытые решения

| Вопрос | Решение | Дата |
|---|---|---|
| Инструмент миграций | **goose** — простые SQL up/down, прямо ложатся на требование forward+rollback | 2026-08-13 |
| Таск-раннер | **go-task** (`Taskfile.yml`) вместо make — ставится как Go-бинарник, работает в PowerShell | 2026-08-13 |
| Авторизация в MVP | Интерфейс `domain.Authorizer` + табличная реализация (`internal/pkg/authz`). Casbin отложен до появления клиента с гранулярными правами — граница та же, кода меньше | 2026-08-13 |
| Подпись токенов | **Ed25519 (EdDSA)**, а не HS256 — чтобы контур тенантов позже проверял подпись по публичному ключу через JWKS без смены схемы | 2026-08-13 |
| Поведение при недоступности Redis **в контуре команды** | **fail-closed** (503). Внутренняя панель: цена ложного отказа несопоставима с ценой пропуска отозванного токена | 2026-08-13 |
| Фронтенд-фреймворк | Refine отклонён в пользу чистого React + TanStack Query/Table + shadcn/ui: для 6–8 CRUD-экранов чужие соглашения дороже выгоды | 2026-08-13 |
| Порядок работы | Бэкенд целиком, фронтенд после него | 2026-08-13 |

## 10. Enterprise-readiness (для роста в крупные контракты)

| Возможность | Статус |
|---|---|
| RBAC (Casbin) | ✅ заложено |
| Audit logs | ✅ заложено |
| MFA (TOTP) | ✅ заложено |
| Rate limiting / brute-force защита | ✅ заложено (см. §7) |
| SSO (вход через корпоративный IdP клиента) | ⬜ добавить, когда появятся крупные сетевые клиенты |
| SOC 2 / ISO 27001 | ⬜ не нужно на старте, но архитектура (audit logs, access control, incident response) должна позволить пройти аудит позже без переделки |
| Status page / SLA | ⬜ добавить перед первыми платящими клиентами |
| Staging environment | ⬜ обязательно до продакшн-релизов |

### Биллинг и монетизация

- Провайдер платежей: Stripe или локальный (Kaspi/Freedom Pay) — зависит от рынка (§9)
- Тарифы уже заложены в `tenant_plan` (starter/growth/enterprise)
- Авто-suspend тенанта при неоплате — через desired-state механизм (§6a), а не
  отдельной логикой + dunning (напоминания, retry failed payments)
- Инвойсинг и налоговая отчётность — юридический вопрос, решается отдельно от кода

### Юридическое

- Terms of Service + Privacy Policy — до первого платящего клиента
- Соответствие законодательству о персональных данных (данные покупателей через
  кассы/операторов целевого сервиса)
- PCI DSS, если/когда в целевом сервисе появится обработка платёжных карт
  (по возможности — делегировать это платёжному провайдеру, не хранить данные карт самим)
