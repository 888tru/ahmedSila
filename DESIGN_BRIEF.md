# Дизайн-бриф суперадминки

## Концепция

Минимализм в духе 1C, но современнее: плотная, предсказуемая, функциональная
информация без визуального шума. Никакой "маркетинговой" эстетики — это
рабочий инструмент, которым команда пользуется каждый день, а не витрина.
Приоритет — скорость считывания данных, а не впечатление с первого взгляда.

Явно НЕ делаем: тёплый кремовый фон с терракотовым акцентом, тёмная тема
с неоновым акцентом, "газетная" вёрстка с тонкими линиями и плотными
колонками — это шаблонные ИИ-дефолты, которые появляются независимо от
содержания. Наш вариант — нейтральный нейтралитет и один сдержанный акцент,
это осознанный выбор под конкретную задачу (плотные данные, ежедневная работа).

## Язык и терминология — ВАЖНО

Продукт для СНГ-аудитории. Всё, что видит пользователь в интерфейсе, — **на
простом русском языке**, без калек с английского и без технического жаргона.

Технические термины (tenant, refresh token, RBAC, JWT и т.п.) остаются
внутри кода и БД — это нормальная индустриальная терминология для
разработки. Но в интерфейсе их быть не должно:

| Технический термин (код) | Что видит пользователь |
|---|---|
| tenant | Клиент / Магазин |
| dashboard | Обзор / Сводка |
| suspend tenant | Приостановить доступ |
| procurement request | Заявка на закупку |
| support ticket | Обращение |
| audit log | Журнал действий |
| refresh token истёк | «Сессия истекла, войдите снова» (пользователь не должен видеть слово «токен») |

Правило простое: если термин можно объяснить продавцу в магазине без
IT-образования — используем его. Если нет — ищем русский аналог.

## Какие данные вообще показываем — ВАЖНО

Суперадминка не видит продажи и выручку клиента — у неё физически нет к этому
доступа. Не проектируем экраны с «оборотом», «средним чеком» и подобным —
это данные из другого мира (кассовые продажи покупателям), к которому
продукт отношения не имеет.

То, что реально показываем:
- **Верхнеуровневые показатели по клиенту**: сколько сотрудников заведено в
  системе, когда клиент последний раз заходил
- **Закупки** — что и по какой цене клиент заказывает у поставщиков через
  заявки операторов. Это главный содержательный показатель. Модель данных под
  него заложена уже в MVP (см. `TECH_STACK.md`), сами данные появятся, когда
  заработает модуль заявок в целевом сервисе — до этого в интерфейсе пустое
  состояние, не отсутствующий раздел
- Никакой детализации по внутренним задачам/сменам/чек-листам сотрудников —
  это операционная кухня клиента внутри его собственной системы, суперадминке
  это не нужно

При проектировании любого нового экрана или метрики — сверяться с этим
списком, не додумывать доступ к данным, которых у продукта нет.

## Палитра

| Роль | Hex | Использование |
|---|---|---|
| Фон страницы | `#F6F6F4` | Тёплый нейтральный серый — меньше усталости глаз при плотных таблицах |
| Поверхность / карточки | `#FFFFFF` | Карточки, таблицы, модалки |
| Граница (hairline) | `#E3E2DD` | 1px, разделители, границы таблиц |
| Граница светлая | `#F0EFEA` | Разделители строк внутри таблиц |
| Текст основной | `#1F1E1B` | Заголовки, значения, основной контент |
| Текст вторичный | `#6B6A64` | Подписи, метаданные, неактивные пункты меню |
| Акцент | `#2F5C8A` | Точечно: активный пункт меню, ссылки, primary-кнопка. НЕ заливка фона |
| Успех (статус) | фон `#EAF3DE` / текст `#3B6D11` | Бейджи статусов («активен») |
| Предупреждение (статус) | фон `#FAEEDA` / текст `#854F0B` | Бейджи статусов («триал», «на паузе, скоро спишем») |
| Опасность (статус) | фон `#FCEBEB` / текст `#A32D2D` | Бейджи статусов («на паузе», «просрочка») |

Никаких дополнительных ярких цветов. Акцент используется точечно, не заливкой.

## Типографика

- **Интерфейс**: Inter или IBM Plex Sans — нейтральный гротеск, хорошая
  поддержка кириллицы, не «модный» шрифт с характером
- **Числовые данные** (суммы, счётчики, колонки таблиц): IBM Plex Mono или
  JetBrains Mono с табличными цифрами — числа выравниваются точно, как в
  бухгалтерском регистре. Это и есть отсылка к 1C, без внешнего копирования стиля
- Размер тела текста: 13–14px (плотно, функционально)
- Заголовки: скромные, 16–20px, без крупного «витринного» типографического акцента
- Только 2 начертания: regular и medium. Никакого bold без необходимости

## Layout

- Фиксированный левый сайдбар: иконка + подпись на русском, сворачиваемый
- Тонкий topbar: хлебные крошки (на русском) + поиск + аватар пользователя
- Основной контент по умолчанию — плотные таблицы, не «воздушные» карточки-плитки
- Закреплённая шапка таблицы при скролле
- Компактная высота строки (32–36px), с возможностью переключить плотность
- Метрики — узкая строка из 3–4 компактных ячеек (число + подпись): активных
  клиентов, открытых обращений, клиентов на паузе/триале — не крупные
  глянцевые KPI-карточки на весь экран, и не финансовые показатели (см. раздел
  «Какие данные вообще показываем»)
- Формы создания/редактирования — модалки или боковая панель (drawer), не
  отдельные страницы для простых операций

## Сигнатурный элемент

«Учётная сетка» (ledger grid): числовые колонки таблиц — моноширинным шрифтом
с табличными цифрами, с чёткой тонкой вертикальной границей между текстовыми
и числовыми колонками. Современная версия бухгалтерского регистра: hairline-
границы вместо толстой сетки, мягкий радиус 4–6px вместо острых углов.

## Анимация

Минимальная, почти отсутствует. Максимум 100мс на смену состояния (открытие
модалки, наведение). Никаких сложных переходов, скролл-эффектов, декоративной
анимации — это принципиальный выбор под «без лишней замудрённости».

## Копирайтинг в интерфейсе

- Глагол в начале действия: «Приостановить доступ», не «Приостановление доступа»
- Кнопки — 1–3 слова, с большой буквы только первое слово: «Создать клиента»
- Ошибки — что произошло и что делать, без «Ошибка:» в начале:
  «Не удалось сохранить. Проверьте соединение и попробуйте снова»
- Пустые состояния — приглашение к действию, не извинение:
  «Пока нет клиентов» + кнопка «Добавить клиента», не «Здесь пока пусто»
