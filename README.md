# Суперадминка

Внутренняя панель управления тенантами (магазинами и супермаркетами) — не
multi-tenant продукт, а один инструмент команды поддержки/продаж, видящий всех
клиентов сразу. Целевой сервис для операторов и кассиров — отдельный проект,
контракт с ним (gRPC) не спроектирован.

Полное обоснование архитектурных решений — в [`TECH_STACK.md`](./TECH_STACK.md),
контекст для дальнейшей разработки (что уже написано, почему именно так, на
какие грабли не наступать) — в [`CLAUDE.md`](./CLAUDE.md).

## Требования

- Go 1.26+
- Node.js 22+
- Docker (для Postgres, Redis и интеграционных тестов на testcontainers)
- [go-task](https://taskfile.dev): `go install github.com/go-task/task/v3/cmd/task@latest`

Остальной тулинг:

```
go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest
go install github.com/pressly/goose/v3/cmd/goose@latest
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest
```

На Windows весь этот тулинг ставится в `%USERPROFILE%\go\bin`, который не
всегда есть в `PATH` — если команда `task`/`sqlc`/`goose` не находится,
добавьте эту папку в `PATH` вручную.

## Первый запуск

```
cp .env.example .env
task gen-keys        # вставить полученные ключи (JWT_PRIVATE_KEY/JWT_PUBLIC_KEY) в .env
task up               # Postgres + Redis (нужен запущенный Docker Desktop)
task migrate-up
task seed              # демо-данные: команда, клиенты, обращения
task run                # backend на http://localhost:8080/healthz

# в отдельном терминале
cd web
npm install
npm run dev             # frontend на http://localhost:5173
```

`task seed` печатает пароль для входа (`password123`, одинаковый у всех
сидовых сотрудников) — залогиниться можно, например, под
`a.kerimov@example.kz` (роль owner, с TOTP-секретом в БД, но 2FA пока нигде не
проверяется принудительно — см. «Что нужно для реального enterprise»).

## Как это работает

### Слои и поток запроса

Clean Architecture, правило зависимостей одностороннее:
`delivery → usecase → domain ← repository`. `domain` — только сущности и
интерфейсы (`AuthProvider`, `Authorizer`, `TenantRepository` и т.д.), без
единого импорта Gin, sqlc или Redis; это проверяется отдельным тестом.
`cmd/server/main.go` — единственное место, где под интерфейсы domain
подставляются конкретные реализации (Postgres-репозитории, Ed25519-подпись,
Redis-хранилище отзыва токенов).

Запрос идёт `Gin router → middleware (auth, authz, audit) → handler →
usecase → repository`. Хендлеры не выбирают HTTP-статус сами — они
возвращают доменную ошибку, а единый маппинг в `internal/delivery/http/response`
переводит `domain.ErrNotFound`/`domain.ErrConflict`/... в конкретный код.
Это гарантирует, что один и тот же тип ошибки не станет в одном месте 404,
а в другом — 400.

### Аутентификация

- Access-токен — JWT, подписанный Ed25519 (EdDSA), живёт 15 минут, хранится
  **только в памяти** фронтенда (не в `localStorage`, чтобы не читался
  произвольным JS при XSS). В заголовке токена — `kid`, под будущую ротацию
  ключей.
- Refresh-токен — непрозрачная случайная строка в httpOnly-cookie с `Secure`
  и `SameSite=Strict` в проде. В БД хранится не сам токен, а его SHA-256 —
  утечка дампа таблицы `refresh_tokens` не даёт войти.
- Каждый refresh — это ротация: старый токен помечается использованным,
  выдаётся новый в той же `session_id`. Если предъявлен уже использованный
  refresh — это признак кражи токена, отзывается **вся цепочка** сессии, а не
  один токен.
- На фронтенде (`web/src/lib/http.ts`) при 401 запускается silent refresh —
  но если несколько запросов словили 401 одновременно, реально уходит только
  один запрос на обновление (остальные ждут тот же `Promise`), иначе
  параллельные refresh-и наперегонки друг друга сами создали бы ложное
  срабатывание reuse-детекции.
- Redis хранит список отозванных access-токенов (logout/logout-all должны
  инвалидировать токен немедленно, а не ждать истечения 15 минут). Если Redis
  недоступен — запросы отклоняются (503), не пропускаются: для внутренней
  панели цена ложного отказа ниже цены пропуска отозванного токена.
- `ErrInvalidCredentials` одинаков для «нет такого email», «неверный пароль»
  и «учётка приостановлена» — иначе login стал бы оракулом существования
  учёток. Для несуществующего email вызывается фиктивная проверка пароля,
  чтобы совпадало и время ответа. Блокировка после N неудачных попыток
  проверяется **после** сверки пароля — иначе «эта учётка заблокирована»
  получает кто угодно, просто угадавший существующий email.

### Права доступа

Четыре роли (`owner`, `admin`, `support`, `viewer`), проверка — через
`domain.Authorizer` и `middleware.Require(resource, action)`, никогда
`if user.Role == "admin"` по коду. Матрица прав — таблица в
`internal/pkg/authz/table.go`, не Casbin: для фиксированного набора ролей
Casbin означал бы model-файл, адаптер и синхронизацию политик между
инстансами ради той же самой расширяемости, которую уже даёт граница
`domain.Authorizer`.

### Аудит

Каждое чувствительное действие (создание/удаление клиента, приостановка,
смена роли сотрудника, ответ на обращение и т.д.) пишется в `audit_logs`
отдельным портом. Ошибка записи в аудит **не** роняет основную операцию —
единственное место, где она видна, это лог самого `AuditRepo`. Запись
денормализована (`actor_email`, читаемое описание действия), чтобы журнал
оставался осмысленным даже после удаления пользователя или клиента.

### Данные и деньги

Postgres через `pgx`/`sqlc` — SQL пишется руками в `internal/repository/postgres/queries/*.sql`,
`sqlc generate` перегенерирует типобезопасный Go-код по нему и по схеме из
`migrations/` (живая БД для этого не нужна). Миграции — `goose`, с явным
down на каждую up. Денежные величины — `bigint` в минорных единицах
(тиынах) плюс отдельная колонка валюты, никакого `float`.

### Фронтенд

React 18 + TypeScript (Vite), Tailwind v4, TanStack Query для всех
запросов/мутаций, TanStack Table v9 (не v8 — API сильно отличается) для
таблиц, React Router v7. Все 8 экранов из [`PAGES.md`](./PAGES.md) реализованы
и подключены к живому API: логин, «Обзор», «Клиенты» (список и карточка со
всеми вкладками), «Обращения», «Журнал действий», «Команда», «Настройки».
Слой аутентификации (`web/src/lib/auth.ts`, `web/src/features/auth/*`) —
самописный стор на `useSyncExternalStore`, без отдельной state-библиотеки.
Ответы бэкенда — конверт `{data}`/`{data, meta}`/`{error}`, распаковывается
централизованно в `web/src/lib/http.ts`; JSON с бэкенда — snake_case, во
фронтенде — camelCase, преобразование явное в каждом `features/*/api.ts`.

Мок-режим (`VITE_USE_MOCK=true`) остался в коде как fallback/для UI-разработки
без бэкенда, но по умолчанию выключен — экраны ходят в реальный API.

### Сознательные упрощения MVP

Не «забыто», а решено не делать сейчас (см. `CLAUDE.md` → «Не делаем в MVP»):
gRPC и `.proto` к целевому сервису, Kubernetes, Casbin, SSO, биллинг, status
page, read replicas, RLS. Внутри уже реализованного тоже есть намеренные
упрощения: у тенантов нет `desired_status`/`observed_status` (это появится
вместе с gRPC-контрактом), дельты метрик на «Обзоре» всегда `null` (нужна
таблица `tenant_metrics_snapshots` и фоновая задача, которых нет), у
приглашения в команду нет реального приёма (accept-flow) и реальной отправки
email/SMS — токен/код только возвращается в ответе API, как и коды
подтверждения у клиентов (это тоже сделано намеренно: коду нужно
перевыдавать/показывать повторно).

## Проверено

- Backend: `go build`, `go vet`, `golangci-lint run` (0 замечаний), `go test ./... -race`
  (юнит-тесты auth-usecase — ротация, reuse-детекция, lockout, изоляция
  сессий, неразличимость ошибок входа).
- Миграции `up`/`down` — на живом Postgres.
- `cmd/seed` — идемпотентен, повторный запуск не плодит дубликаты.
- Frontend: `npm run build` (tsc + vite), `npm run lint`.
- Полный ручной прогон в браузере: логин → все 8 экранов с реальными
  мутациями → logout → повторный логин → жёсткая перезагрузка страницы
  (сессия переживает reload за счёт silent refresh).
- CI (`.github/workflows/ci.yml`) гоняет то же самое на каждый push/PR:
  backend — lint, vet, test -race, `govulncheck`, сборка Docker-образа;
  frontend — lint, build.

## Что нужно для реального enterprise

Ниже — не баги, а осознанные пробелы между текущим MVP и продакшен-готовой
enterprise-системой. Сгруппировано по темам.

### Безопасность

- **Secrets management.** Сейчас ключи и пароли — в `.env`. Для прода нужен
  реальный secrets manager (см. открытый вопрос в `TECH_STACK.md` §9) вместо
  переменных окружения контейнера напрямую, плюс процесс их ротации (`kid`
  в JWT-заголовке под это уже заложен, но ротация не реализована).
- **2FA не принудительна.** В схеме БД есть `totp_secret`/`totp_enrolled_at`
  и `Role.RequiresTOTP()`, но при логине второй фактор нигде не проверяется —
  это включённая в схему, но не подключённая к потоку входа возможность.
- **Rate limiting только по email.** Есть lockout после N неудачных попыток
  для конкретной учётки, но нет rate limit по IP/сети — брутфорс по многим
  email одновременно ничем не ограничен.
- **Аудит-лог не immutable.** Это обычная таблица; для реального
  compliance-уровня (SOC2 и т.п.) нужен append-only storage или экспорт в
  отдельное неизменяемое хранилище — сейчас запись можно отредактировать
  тем же доступом, что у обычной БД.
- **Нет SSO/OIDC.** Явно отложено в MVP; для enterprise-клиентов обычно
  требуется вход через Okta/Azure AD/аналоги.
- **Нет автообновления зависимостей** (Dependabot/Renovate) — `govulncheck`
  в CI ловит уже известные уязвимости, но не держит зависимости свежими сам.
- **WAF/CDN перед публичным API** — инфраструктурное решение, не принято.

### Надёжность и observability

- **`/healthz` — только liveness.** Нет readiness-проверки, которая бы
  учитывала доступность Postgres/Redis отдельно от факта, что процесс жив.
- **Нет распределённой трассировки** (OpenTelemetry) — есть `request_id` в
  структурных логах, но нет корреляции между спанами, тем более полезной,
  когда появится gRPC-вызов к целевому сервису.
- **Логи никуда не агрегируются** — structured-логи есть, но не уходят в
  централизованную систему (Loki/ELK/Datadog и т.п.), нет дашбордов и
  алертинга (Prometheus/Grafana или managed APM).
- **Нет документированного backup/restore** — ни расписания бэкапов, ни
  PITR-стратегии для Postgres.
- **Read replicas** — явно не делаем в MVP; масштаб текущей схемы упрётся
  в это первым.
- **Graceful shutdown есть, readiness gate — нет.** Сервер корректно
  обрабатывает SIGTERM, но балансировщик не узнаёт заранее, что нужно
  перестать слать новый трафик до начала остановки.

### Тестирование

- **Testcontainers-интеграционные тесты репозиториев** — запланированы
  (`task test` уже рассчитан на них), но не написаны; сейчас усечённый
  `task test-unit` покрывает только usecase-слой на фейках.
- **Нет e2e фронтенда** (Playwright/Cypress) — весь UI-регресс сейчас
  проверяется вручную через браузер.
- **Нет нагрузочного тестирования** (k6/Gatling) и contract-тестов под
  будущий gRPC-контракт с целевым сервисом.

### Масштабируемость и функциональность

- **Списки не пагинированы** (`GET /clients`, `/tickets`, `/team`) — нормально
  при текущих объёмах, но потребует пагинации/курсоров при росте.
- **Нет кэширования на чтение** — Redis используется только под revocation
  list токенов, не как read-cache.
- **Приём приглашения в команду не реализован** — owner видит токен
  приглашения, но flow принятия приглашения самим сотрудником отсутствует,
  как и реальная отправка email/SMS (см. «Сознательные упрощения MVP» выше).
- **Дельты метрик на «Обзоре» всегда `null`** — нужна таблица снапшотов и
  фоновая задача их считающая.
- **gRPC-контракт с целевым сервисом** не спроектирован — появится, когда
  target-service дойдёт до интеграции.

### DevOps

- **CI есть, CD — нет.** `.github/workflows/ci.yml` уже проверяет
  lint/vet/test/vulnscan/docker-build (backend) и lint/build (frontend) на
  каждый push, но автодеплоя и staging-окружения нет.
- **Docker-образ готов** (`Dockerfile`: multi-stage, distroless non-root),
  но манифестов деплоя (Terraform/Helm) и выбранного хостинга нет — это
  открытый вопрос в `TECH_STACK.md` §9.
- **Нет feature flags** — любое изменение сразу становится видно всем.

## Полезные команды

| Команда | Что делает |
|---|---|
| `task` | список всех задач |
| `task up` / `task down` / `task reset` | поднять / остановить / снести контейнеры Postgres+Redis |
| `task migrate-up` / `task migrate-down` / `task migrate-status` | миграции |
| `task migrate-new -- add_something` | новая миграция |
| `task sqlc` | перегенерировать код доступа к БД после правки SQL-запросов |
| `task gen-keys` | сгенерировать Ed25519-ключи для JWT |
| `task seed` | наполнить БД демо-данными (команда, клиенты, обращения) |
| `task run` | backend-сервер на `:8080` |
| `task web-dev` | dev-сервер фронтенда (то же, что `cd web && npm run dev`) |
| `task test` | все тесты, включая интеграционные (нужен Docker) |
| `task test-unit` | только быстрые тесты, без Docker |
| `task lint` | golangci-lint |
| `task check` | всё, что гоняет CI: `lint` + `test` |

## Структура

```
cmd/server                     сборка графа зависимостей (main.go — единственное
                                место, где выбираются конкретные реализации)
cmd/genkeys                    генерация Ed25519-ключей
cmd/seed                       демо-данные: команда, клиенты, обращения

internal/domain                сущности и порты (интерфейсы); не импортирует
                                Gin, sqlc, Redis
internal/usecase                бизнес-логика поверх портов domain
internal/repository/postgres    репозитории поверх sqlc; queries/ — исходный SQL
internal/repository/sqlc        сгенерированный код, руками не править
internal/delivery/http          Gin: router, middleware, handler, response
internal/pkg                    jwt, authz, authprovider, hash, config, redisx

migrations                      SQL-миграции (goose)

web/src/components              оболочка (сайдбар/topbar) и общие UI-примитивы
web/src/features                экраны по областям: auth, overview, clients,
                                 tickets, journal, team, settings — в каждой
                                 features/<name>/api.ts (обёртка над бэкендом)
                                 и хуки на TanStack Query
web/src/lib                     http.ts (fetch + envelope + silent refresh),
                                 auth.ts (стор токена/пользователя),
                                 форматирование дат/чисел, склейка классов
```

Правило зависимостей: `delivery → usecase → domain ← repository`.
